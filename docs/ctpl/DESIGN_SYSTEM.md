# CTPL Design System Notes

What's shared with the general design system versus what's specific to CTPL. See [`../general/DESIGN_SYSTEM.md`](../general/DESIGN_SYSTEM.md) for the app-wide design language (dark mode, card/table conventions, `Section`/`FieldGrid`/`Field` UI kit) this document assumes as a baseline.

## 1. Branding

CTPL uses the **Non-Life** brand, shared with OFW and GTP (not PD Life's red): navy `#002f6c` for headings/primary actions/emphasis text, light blue `#49b1ea` for the dark-mode equivalent and secondary accents. Applied via `src/lib/brand.ts`'s product-branding resolution, same mechanism used by Maintenance's product re-skin. Nothing about CTPL's own components hardcodes a different palette — every `text-[#002f6c] dark:text-[#49b1ea]` occurrence across `ctpl_*.tsx` is the same brand-neutral pattern used by `ofw_*`/`gtp_*` components, not a CTPL-specific color.

CTPL's icon is `Car` (lucide-react) — used in the sidebar, dashboard header, and application list header, consistently identifying the product line at a glance the way OFW uses a different icon for its own nav entry.

## 2. Reused vs CTPL-specific patterns

**Reused wholesale from the general/shared system:**
- `Section` / `FieldGrid` / `Field` (from `application_detail_ui.tsx`) — the icon-header + read-only field-grid pattern used across PD Life, OFW, and CTPL detail views alike. CTPL's detail/list-view pages use these with `hideEditButton` for read-only sections.
- `PolicyDocumentsSection` / `PrintableDocumentModal` / `DocRow` (`policy_documents.tsx`) — the "documents unlock once paid" locked/unlocked pattern, and the printable-modal chrome (letterhead, Print/Close buttons). CTPL uses the locked/unlocked gating exactly as OFW/GTP do; it diverges only in what happens on "View" (see §4).
- Status/policy-status badge styling conventions (colored pill badges keyed off enum value) — same visual language as OFW's Paid/Unpaid + policy-status badge stack.
- The Review-step-before-submit wizard pattern, and its accompanying `cardClass`/`sectionHeadingClass`/`inputClass`/`labelClass` constants — identical in spirit and mostly identical in Tailwind classes to GTP's create-application wizard.
- Cascading Region → City → Barangay address selects (`ph_geography.ts`) — shared geography data, used identically in the create wizard, the unpaid detail edit form, and endorsement editing.

**CTPL-specific:**
- **The vehicle picker.** Year and Make are dropdowns sourced from a maintained reference list (`ctpl_vehicle_reference.ts`) rather than free text — no other product line in this app has an equivalent "maker/model" picker pattern, since OFW/GTP have no vehicle concept at all. Series/Color/Body Type/Motor Number/Authorized Capacity/Unladen Weight remain free-text inputs alongside the two constrained dropdowns, deliberately: the dropdowns exist specifically to reduce mismatches on the two fields ctpl.ph itself constrains (year, maker), while the rest stay free-text because either ctpl.ph's own catalog is too large to mirror (trim/Series) or there's no authoritative source to constrain against (color, body type, etc.).
- **Two different detail-view components depending on payment state**, rather than one component with an `isPaid` prop branching internally: `ctpl_application_list.tsx` renders the paid quick-preview inline; unpaid applications route to the wholly separate `ctpl_application_detail.tsx`. This split exists because an unpaid application needs a real edit mode (form fields, Save/Cancel) that a paid, already-issued policy has no business exposing — a paid COC shouldn't be silently editable client-side. Structurally this is a deliberate two-component design, not a shortcut.
- **Real generated-PDF view/print flow.** CTPL's "View/Print" and "Send to Client" document actions call the real `/api/documents` list+presign endpoints and `window.open()` the actual generated PDF in a new browser tab. This replaces the older `PrintableDocumentModal` in-app mock-template render (a hand-built HTML "printable document" using `DocRow` rows) that OFW's COI section and GTP's whole document section still use — those products render a fabricated approximation of the document inside the app, because they have no real fill service backing them yet (see `ARCHITECTURE.md` §1). CTPL's unpaid detail page (`ctpl_application_detail.tsx`) still keeps a `PrintableDocumentModal` wired up for parity/fallback, but it's unreachable in practice since documents there are always locked (`isPaid={false}` is hardcoded on that page's `PolicyDocumentsSection`).
- **Embedded Endorsements UI inside the paid quick-preview** (`CtplPolicyEndorsements`) — a policy-scoped endorsement history + "New Endorsement" action, nested inside the Documents & Endorsements section. No other product line has this UI element yet (OFW's own endorsements list, per the recent "feat: add OFW policy endorsements list UI" commit, is UI-only so far — it doesn't yet have CTPL's backing calculation/document services).
- **The COV (Certificate of Validation) badge and note.** A small amber "COV Availed" pill and inline verification-fee note appear only on CTPL screens (create wizard, detail view, quick preview) — this is a CTPL-only add-on concept with no OFW/GTP equivalent.

## 3. Layout conventions specific to CTPL pages

- Both the paid quick-preview and the unpaid detail page render as a **full page**, not a centered scrollable modal — explicitly chosen (per in-code comments) so neither view needs an inner scroll box regardless of how much content a given application has, and so the URL can point at a specific application (`/ctpl/applications/<referenceNo>`) the way a real page would.
- The create-application wizard's header keeps a persistent right-aligned running total ("Estimated Premium" pre-review, "Total Amount Due" once COV is selected) — visible at every scroll position, not just at the bottom summary, so the client-facing "this is what you're about to pay" framing carries through the whole form.
- Toast notifications (bottom-right-fixed... actually top-right-fixed, `fixed top-6 right-6`, emerald background, 2.5s auto-dismiss) are used consistently across the CTPL list/detail pages for transient confirmations (documents sent, remarks saved, endorsement submitted) — same pattern as other product lines, not CTPL-specific, but worth noting since CTPL's document/endorsement actions are the ones most likely to trigger one.
